# 渠道贡献归因工作台（Channel Attribution Workbench）

面向电商投放分析师与投放负责人的**渠道贡献分析、订单回查与模型评估**前端应用。基于 React 18 + TypeScript + Vite + ECharts 实现，纯前端工程（无后端依赖，数据服务以异步模块模拟），所有运行、共享、预算方案、模型评估与审查记录通过 `localStorage` 持久化。

> 所有归因结果都是**规则分摊**，用于渠道间相对比较与订单级回查，**不代表渠道因果关系**。
>
> 模型评估模块的核心立场：**没有可观测的真实渠道贡献标签**。评估只回答「计算是否正确」「结果是否稳定」「差异来自模型还是输入」，**不输出准确率、不发布因果效果、不自动调整投放**。净收入守恒、份额稳定或某渠道金额上升，都不能当作模型准确率。

## 1. 技术栈

| 层 | 选型 |
| --- | --- |
| 框架 | React 18 + TypeScript 5（strict） |
| 构建 | Vite 5 |
| 图表 | Apache ECharts 5（独立分包） |
| 路由 | react-router-dom 6（HashRouter，兼容静态托管） |
| 状态 | zustand 4（persist 中间件，localStorage，带版本迁移） |
| 时间 | 原生 `Intl` 时区格式化 |
| 测试 | Vitest（引擎纯函数 / 竞态 / 存储工作流 / SSR 冒烟） |
| 部署 | 多阶段 Dockerfile + docker-compose（nginx 托管 SPA） |

金额全部以**整数分**存储与计算，展示层格式化为元，杜绝浮点误差。稳定性计算使用**可复现的伪随机数发生器**（mulberry32），同一种子得到同一抽样，成对差异可复核。

## 5. 模型评估模块的能力对照

| 需求要点 | 实现位置 |
| --- | --- |
| 模型登记：规则、允许用途、修订 | `/evaluation` 模型登记页签；`ModelRegistryEntry` / `ModelRevisionRecord`；修订哈希 `engine/registry.ts` |
| 样本清单固定订单、授权触点、退款观察截止点、成熟条件 | `SampleDefinition` + `engine/sample.ts: buildSample`；样本哈希 `sampleFingerprint` |
| 评估引擎输出订单级差异与分群指标 | `engine/evaluation.ts: evaluate / segmentAnalyses / buildOrderDiffs` |
| 成熟共同样本做版本比较，近期窗口做漂移监测，两窗口不混排 | `SampleWindow`、`startEvaluationRun` 拒绝「近期窗口 + 版本比较」；`driftReport` |
| 逐单守恒，退款负额 / 未知渠道 / 无授权触点分别说明 | `ModelEvaluation.conservation / negativeAllocations / overRefund / unknown.byReason / coverage` |
| 渠道份额、订单分配差异、有效触点覆盖，按区域/设备群分解 | `ChannelShare`、`OrderDiff`、`CoverageBreakdown`、`SegmentAnalysis` |
| 稳定性按客户簇/订单簇重复抽样，成对运行两模型，差异区间 | `engine/evaluation.ts: stabilityAnalysis`（簇内订单与同批退款整体保留） |
| 缺可靠跨设备关系只能按订单簇并说明限制，不拼接身份 | `buildSample` 客户簇 vs 订单簇回退；`clusterNote`、`limitations` |
| 样本不足 / 渠道未覆盖 / 区间无法确定 → 不支持结论，不填零分 | `SupportState`；`SupportBadge`（页面上显示原因） |
| 构成变化先共同权重比较，再单列新增/缺失群；不以总均值掩盖局部退化 | `compositionComparison`；总体 vs 局部方向相反单独标注 |
| 导入订单/触点/退款补充样例，预览纳入/排除原因后启动评估 | 导入补充样例弹窗 + 样本预览（纳入 / 排除明细） |
| 长计算显示进度并可取消；切换样本旧任务不得覆盖新结果 | `services/evaluationService.ts: startEvaluation`；store 中旧任务标记取消且结果丢弃 |
| 退款补齐生成新样本；报告分别对照换模型 / 换样本 / 只更新退款 | `refreshSampleRefunds` + `buildComparisons`（`model_swap` / `sample_swap` / `refund_update`） |
| 发布与批准撤回并发时重新检查模型与样本修订 | `verifyReviewRefs` + 发布前复核；撤回后 `validForNewAnalysis=false` |
| 撤回后旧报告仍可回看，但不能供新分析作为有效性证明 | 冻结结果保留；审查页显示「不可用于新分析」 |

## 6. 推荐验证路径（覆盖全部评估需求）

### 场景 A：成熟共同样本上比较两个模型（计算是否正确 + 结果是否稳定）

1. 进入 **模型评估** 页 → **评估样本** 页签。
2. 样本选择 `SMP-MATURE-2026-11`，模型 A = 末次触点规则，模型 B = 首次触点规则，用途 = 版本比较。
3. 下方 **纳入 / 排除预览** 展示：纳入订单、净收入、**未成熟退款 O-2105 被排除（等待退款 R-1030 入账）**、已取消 O-2008 排除原因、各渠道覆盖（联盟流量、自然流量显示「从未覆盖 · 不支持结论」）、分群构成权重。
4. 点击「启动评估」，**评估运行** 页签显示进度条与「取消」按钮。
5. 完成后进入 **评估结果与分群**：
   - 两个模型的「逐单守恒」均显示通过；已分配 + 未知 = 净收入。
   - 稳定性明细给出每个渠道份额差异的 95% 区间；未覆盖渠道显示「渠道未覆盖 · 不支持结论」，区间为空而非 0。
   - 分群下钻可切换区域 / 设备群；页面用橙色卡片单独列出「总体与局部方向相反」（如展示广告总体上升、但华北群下降），并写明不能以总均值掩盖。
   - 版本对照「同样本换模型」：两侧样本哈希一致，差异只能来自模型规则，列出变化订单。

### 场景 B：近期窗口漂移监测（更早发现退化，但不混入排行榜）

1. 样本选择 `SMP-RECENT-2026-11`，用途 = **漂移监测**（若强行选择「版本比较」会被拒绝，提示「两个窗口不混排」）。
2. 模型 A/B 任选，启动评估。
3. 进入 **漂移监测** 页签：
   - 表格对比成熟 vs 近期份额漂移，并显示近期覆盖（样例中「展示广告」份额从成熟窗口约 20.5% 升至近期约 44.5%，社交流在近期从未覆盖）。
   - 显示「近期窗口未成熟订单 O-2203（退款未入账，等待退款观察完成）」。
   - 构成变化单列新增群（Tablet）与缺失群（西部）。
   - 页面明确写：漂移仅提示近期退化方向，不并入版本排行榜。

### 场景 C：退款补齐生成新样本修订 + 三类对照

1. 先在成熟样本完成一次评估并生成审查（**审查依据** 卡片 → 生成审查记录 → 赵明批准 → 发布）。
2. 回到评估样本页，点「导入补充样例」→「导入内置迟到退款补充」（批次 `SUP-REFUND-1010`，退款 R-1010 对应 O-2111）。
3. 点「退款补齐生成新样本修订」→ 出现 `SMP-MATURE-2026-11-R2`（rev 2，`supersedes` 指向原样本）。
4. 在新样本上再跑一次评估：版本对照同时包含「同样本换模型」与「只更新退款」（成员不变、净额变化，`isolatedFactor=refund`）。
5. 打开旧审查：冻结结果的净额与样本哈希保持不变（旧审查保留原结果）。

### 场景 D：审查 / 发布 / 撤回与并发复核

1. 对已完成评估点「生成审查记录」→ 状态「待审批」，审计轨迹记录引用模型修订哈希与样本哈希。
2. 以赵明身份「批准」→ 冻结结果（渠道份额、分群、版本对照）；「发布」→ 状态已发布。
3. **模型升级复核**：在模型登记页为末次触点规则登记新修订 `v2`。此后试图批准/发布引用旧修订的审查会被**阻断**（红色「发布阻断」），旧审查标为「不可用于新分析」。
4. **并发撤回**：已发布审查被撤回后，再次发布会被阻断；旧报告仍可「查看冻结内容」回看，但 validForNewAnalysis=false。

### 场景 E：渠道全未知 / 样本不足 / 用途未登记（不填零分）

1. 样本选择 `SMP-EDGE-UNKNOWN`（11-03，所有订单都落入未知来源），启动评估：
   - 逐单守恒仍通过，但所有渠道显示「渠道未覆盖 · 不支持结论」。
   - 未知来源按原因分别说明：无人员标识（O-2401）/ 无订单级触点（O-2403）/ 触点全被排除（O-2402）。
2. 模型 B 选择「品牌保守规则（仅漂移监测）」，用途 = 版本比较：其渠道指标全部显示「模型不允许该用途 · 不支持结论」。

### 场景 F：计算中切换样本（旧任务不得覆盖新结果）

1. 在成熟样本上启动一个评估（进度未完成）。
2. 立刻切到另一个样本再启动评估：旧评估被标记「已取消 / 已被新评估取代」，其结果不会写入；新评估正常完成。

## 9. 已知边界

- 数据为内置样例，模拟异步延迟以暴露真实竞态；接入真实后端时替换 `services/api.ts` 与 `services/evaluationService.ts` 即可，领域模型与引擎不变。
- 持久化位于浏览器 localStorage；多分析师并发在真实系统中应由后端乐观锁/版本号承载，本应用通过独立草稿、修订核对与发布前复核表达该规则。
- 预算模拟采用显式弹性规则，是方案对比工具，不预测真实收入。
- 评估模块**不提供真实贡献标签**，因此不存在可输出准确率的评测集；页面对所有不可下结论的边界显示「不支持结论」并给出原因，绝不填零分。
- 稳定性区间的覆盖率为名义 95%（百分位法），未做多重比较校正；页面提示区间仅刻画抽样波动、不代表准确率。
